# ISyCode Mobile Host API v1

**Status: proposal for host/client coordination.** This document records the
current mobile client behavior and proposes the complete versioned contract
needed before remote sessions are exposed. Only health, one-time pairing
exchange, and client heartbeat are currently implemented by the mobile client.
The other routes below are not called by the app and must not be treated as
available until ISyCode implements and verifies them.

The contract is owned by ISyCode. ISyCode discovers runtimes, authorizes every
operation, owns sessions and approvals, and streams authoritative events. The
mobile app displays host state and requests approval; it is never an authority.
The existing Bridge is not part of this contract and must not be used as an
authorization source.

## Deployment URL and route mounting

The mobile client accepts a base URL with an optional path prefix. For private
Tailscale Serve, the configured base URL and all effective client request URLs
are:

```text
Base URL: https://<verified-tailnet-dns-name>/isycode
GET      https://<verified-tailnet-dns-name>/isycode/v1/health
GET      https://<verified-tailnet-dns-name>/isycode/v1/status
POST     https://<verified-tailnet-dns-name>/isycode/v1/pair/exchange
```

The client preserves `/isycode` and appends `v1/...`. It does not assume a proxy
strips the prefix. Before enabling the route, the host must verify whether its
Tailscale Serve `--set-path=/isycode` mapping forwards the suffix unchanged or
rewrites it, and make the Gateway/host router accept the resulting path. No
Serve route was enabled or remotely tested for this mobile change.

There is a deployment mismatch to resolve: the existing Mobile Host v1 document
describes a TUI-owned service on `127.0.0.1:8765`, while the current private
Serve worktree maps `/isycode` to the Gateway at `127.0.0.1:8787`. The Gateway
must either host/proxy the mobile API under the externally visible
`/isycode/v1/...` paths, or the host must provide a deliberately configured
private route to the Mobile Host. Pointing the app at the Gateway does not by
itself make the Gateway a Mobile Host.

HTTPS is mandatory off-device/over the tailnet and certificates must validate
on iOS. HTTP is allowed by the app only for loopback development. Tailscale
Serve provides private network reachability only: it does not authenticate a
device, issue app credentials, or grant access to Gateway, files, MCP, a
workspace, runtime, or action.

## Common conventions

- API version: `v1`; JSON uses UTF-8 and `application/json`.
- Time values: RFC 3339 UTC, for example `2026-09-29T18:30:00Z`.
- IDs: opaque strings generated by the host; clients must not infer authority
  from an ID or a runtime being present in inventory.
- Authenticated routes use `Authorization: Bearer <device_token>` over trusted
  HTTPS. The token is a device credential, never a Gateway API key or provider
  key. Return its raw value only once during exchange or renewal; store only a
  verifier/digest server-side, keep it in iOS Keychain client-side, and redact
  it from logs and diagnostics.
- The host rechecks device status/scopes, session ownership, workspace grants,
  runtime grants, action grants, and IsySentinel policy for every request.
  Missing, expired, revoked, ambiguous, or unavailable authorization is denied.
- The mobile client cannot elevate scopes or synthesize host state. A successful
  HTTP response means only what that route explicitly documents.

### Error envelope

Errors use a short, non-secret JSON body. The server must not return stack
traces, tokens, provider credentials, filesystem paths, or raw subprocess output.

```json
{
  "error": {
    "code": "credential_expired",
    "message": "Pair this device again.",
    "request_id": "req_opaque"
  }
}
```

`request_id` is optional. Stable error codes include `invalid_request`,
`pairing_expired`, `pairing_rate_limited`, `credential_invalid`,
`credential_expired`, `credential_revoked`, `scope_denied`, `not_found`,
`conflict`, `approval_required`, `approval_expired`, `policy_denied`,
`runtime_unavailable`, `session_closed`, `cursor_expired`, and `temporarily_unavailable`.

## Routes

### 1. Health and authenticated host status

`GET /v1/health` — no auth. Minimal liveness only; must not expose PIN,
connected devices, workspace names, or credentials.

```json
{"service":"isycode-mobile-host","api_version":"v1","state":"alive"}
```

`GET /v1/status` — bearer plus `host:status` (operator-only; not granted by
pairing). Device credentials cannot query operator status. Device-scoped
heartbeat is the supported mobile connectivity signal.

```json
{
  "state":"alive",
  "api_version":"v1",
  "pairing":{"pending":true,"expires_at":"2026-09-29T18:35:00Z"},
  "connected_clients":[{"device_id":"dev_opaque","label":"iPhone","last_seen_at":"2026-09-29T18:31:00Z"}]
}
```

### 2. Pairing and device credentials

`POST /v1/pair/exchange` — unauthenticated except for the one-time pairing PIN.
The PIN is six decimal digits, expires in five minutes, is consumed once, has a
bounded attempt count, and is never returned by health. Existing host v1
behavior documents limits of five failures per peer per minute and twenty
failures per PIN lifetime; `429` includes `Retry-After`.

Request:

```json
{"code":"123456","device_name":"Danny's iPhone","device_id":"<stable-random-id>"}
```

`device_id` is an opaque random installation ID (UUID); `device_name` is a
display label and must not be trusted as identity. Response `201` (raw secret
once):

```json
{
  "api_key":"<random-device-bearer-secret>",
  "device_id":"dev_opaque",
  "key_id":"key_opaque",
  "expires_at":"2026-09-29T19:30:00Z",
  "scopes":["client:heartbeat","runtime:read"]
}
```

For wire compatibility this v1 schema retains the existing `api_key` field
name. Its value is exclusively a random device bearer credential; it is not a
Gateway API key or provider key. The accepted scopes must be explicit grants
from the host; runtime inventory does not imply runtime selection or execution
permission.

`POST /v1/devices/credentials/renew` — bearer for an active device credential
with `device:renew`; rotates the token and invalidates the old token atomically.
Response `200` uses the same credential fields as exchange. Do not return the
new raw token again.

`DELETE /v1/devices/credentials/current` — bearer for the current credential
with `device:revoke`; revokes it and all its live sessions. Response `204`.
Local “forget” is not remote revocation and must be labelled accordingly if the
route is unavailable.

The existing host implements exchange and local keystore digest storage, but
the described v1 slice has no credential renew/revoke endpoints. Pair-issued
credentials expire after one hour in that slice.

### 3. Runtime inventory

`GET /v1/runtimes` — bearer plus `runtime:read`.

```json
{
  "runtimes":[
    {"runtime_id":"codex","display_name":"Codex","installed":true,"adapter":"ready","selectable":true},
    {"runtime_id":"opencode","display_name":"OpenCode","installed":true,"adapter":"pending","selectable":false}
  ]
}
```

Only installed runtimes with an operational adapter may report `selectable:true`.
Selection remains a request, not authority:

`POST /v1/runtimes/select` — bearer plus `runtime:select` and a host grant for
the selected runtime. Request `{"runtime_id":"codex"}`. Response `200`:
`{"runtime_id":"codex","selected":true}`; `409 runtime_unavailable` when
inventory has no operational adapter. The server revalidates inventory and
grants at selection and at every later action.

The current host slice reports adapters pending and no runtime as selectable;
selection returns `409`. The mobile UI must preserve that truth.

### 4. Sessions

`POST /v1/sessions` — bearer plus `session:create`, `runtime:select`, and host
grants for the requested workspace and runtime. Request:

```json
{"workspace_id":"ws_opaque","runtime_id":"codex","title":"Fix the build"}
```

Response `201`:

```json
{"session_id":"ses_opaque","workspace_id":"ws_opaque","runtime_id":"codex","state":"idle","created_at":"2026-09-29T18:31:00Z","event_cursor":"0"}
```

`GET /v1/sessions?state=active&after=<opaque-cursor>&limit=50` — bearer plus
`session:read`. Response `200`:

```json
{"sessions":[{"session_id":"ses_opaque","workspace_id":"ws_opaque","runtime_id":"codex","state":"running","updated_at":"2026-09-29T18:32:00Z"}],"next_cursor":null}
```

`POST /v1/sessions/{session_id}/close` — bearer plus `session:close` and
ownership/grants for that session. Response `200`:
`{"session_id":"ses_opaque","state":"closed","closed_at":"..."}`.
Closing is distinct from cancelling an in-flight turn; close must stop new
turns and report whether a running turn was cancelled or drained.

No session routes exist in the currently implemented host slice.

### 5. Conversation stream and events

`GET /v1/sessions/{session_id}/events?after=<event_id>` — bearer plus
`session:read`; `Accept: text/event-stream`. Each SSE event has a stable,
monotonically ordered per-session `id`, a `event:` name, and JSON `data:`. The
stream replays events strictly after `after`, then continues live. Event IDs
are opaque cursors, not authorization tokens.

Minimum event types:

```text
event: turn.started
data: {"session_id":"ses_opaque","turn_id":"turn_opaque"}

event: message.delta
data: {"session_id":"ses_opaque","turn_id":"turn_opaque","message_id":"msg_opaque","role":"assistant","text":"..."}

event: tool.started
data: {"session_id":"ses_opaque","turn_id":"turn_opaque","action_id":"act_opaque","tool":"bash","summary":"Run approved command"}

event: approval.requested
data: {"approval_id":"apr_opaque","session_id":"ses_opaque","turn_id":"turn_opaque","action_id":"act_opaque","summary":"...","expires_at":"..."}

event: turn.completed
data: {"session_id":"ses_opaque","turn_id":"turn_opaque","final_message_id":"msg_opaque"}

event: turn.failed
data: {"session_id":"ses_opaque","turn_id":"turn_opaque","code":"runtime_unavailable","message":"..."}
```

The host must define durable event ordering, duplicate handling, retention, and
replay bounds. `410 cursor_expired` requires the client to fetch an authorized
session snapshot and resume from its returned cursor; it must not silently
pretend the stream was continuous. A transport reconnect uses the last fully
processed event ID. Heartbeat comments may keep intermediaries alive but are
not conversation events. No stream route exists today.

### 6. Turn cancellation

`POST /v1/sessions/{session_id}/turns/{turn_id}/cancel` — bearer plus
`turn:cancel` and session/workspace/runtime authorization. Request:

```json
{"reason":"user_requested"}
```

Response `202`:
`{"turn_id":"turn_opaque","state":"cancelling","accepted_at":"..."}`.
The client displays “cancelling” until an authoritative terminal event reports
`turn.cancelled`, `turn.completed`, or `turn.failed`. A cancel request is not
proof that execution stopped. Repeated cancel is idempotent and returns the
current state. No cancel route exists today.

### 7. Action approvals

`GET /v1/approvals/{approval_id}` — bearer plus session read/approval visibility
grant; returns `200` with state, action summary, exact bounded parameters
needed for informed consent, expiry, and decision receipt; no hidden secrets.

`POST /v1/approvals/{approval_id}/decision` — bearer plus
`approval:decide`, same device/session ownership, unexpired request, and host
IsySentinel policy. Request:

```json
{"decision":"allow_once","decision_id":"<client-generated-uuid>"}
```

`decision` is `allow_once` or `deny`. Response `200`:
`{"approval_id":"apr_opaque","state":"approved","decision":"allow_once","decided_at":"..."}`
or corresponding `denied` state. Idempotency key reuse with a different body
returns `409 conflict`. Approval is not successful execution: the client waits
for the host's subsequent action/turn result and reports that result only.
Timeout, revocation, disconnect, policy denial, or malformed decision fail
closed. No approval routes exist today.

## Expiry, limits, and reconnection

- Pairing PIN lifetime: five minutes, one successful exchange, bounded attempts;
  expired/consumed PIN returns `410 pairing_expired`; throttling returns `429`
  with `Retry-After`.
- Device bearer lifetime: host-issued `expires_at`; expired returns `410`,
  revoked/invalid returns `401`. Never refresh by silently replaying a PIN.
- Per-route limits must be documented by the host and return `429` with
  `Retry-After`; mutations should accept an idempotency key where retry could
  duplicate side effects.
- Heartbeat uses `POST /v1/clients/heartbeat` with
  `{"client_id":"<stable-install-id>","device_name":"iPhone"}` and bearer
  scope `client:heartbeat`; success `200` or `204`. It proves only recent client
  liveness. Existing host behavior uses a 45-second in-memory lease; the app
  currently sends every 15 seconds while foregrounded and pauses in background.
- On reconnect, check unauthenticated health, then authenticate by heartbeat,
  then resume each authorized event stream from its last processed cursor. A
  health success is not proof of a valid credential. `401`/`410` stops retries
  and asks for re-pairing; network failures use bounded exponential backoff
  with jitter; `429` honors `Retry-After`.
- Client “forget” currently deletes local Keychain material only. Until remote
  revocation is implemented, the user must revoke that device at the host.

## Current implementation and compatibility blockers

The mobile client currently implements only `GET /v1/health`,
`POST /v1/pair/exchange`, and `POST /v1/clients/heartbeat`. It saves the bearer
secret in Keychain and non-secret credential metadata in app preferences. It
has no status, renew/revoke, runtime, session, stream, cancel, or approval
client methods, and it intentionally exposes no remote execution UI.

The pairing response uses the existing `api_key` wire field for a device bearer
credential; its legacy name must not cause the host to accept a Gateway or
provider key. The app's “forget” action is local-only. Pair-issued `runtime:select`
must not be treated as permission to execute; the new host must issue narrow
grants and check IsySentinel per action.

The current Serve branch owns a `/isycode` route to Gateway port `8787`; the
older host contract describes a Mobile Host on `8765`. ISyCode must decide which
process handles the `/isycode/v1/...` URLs, document exact upstream URI rewrite
semantics, bridge the existing host protocol if appropriate, and reconcile the
two credential field names. Until then the remote pairing/stream experience is
**not demonstrated**. No Serve state was changed and no remote device test was
performed for this document.
